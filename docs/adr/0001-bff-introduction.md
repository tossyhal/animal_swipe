# ADR 0001: 外部動物 API を集約する BFF を導入する

- ステータス: 承認済み（実装フェーズ 1〜4 完了、フェーズ 5 未着手）
- 日付: 2026-07-27
- 関連 Issue: #45（本 ADR）、#15、#17、#34、#35、#44

## 背景

`lib/services/api_service.dart` は Flutter クライアントから外部 API を直接呼び出している。

- `cat`: `GET https://cataas.com/api/cats?limit=10&skip={0..999}`
- `dog`: `GET https://dog.ceo/api/breeds/image/random/10`

この構成には次の問題がある。

1. **API ごとの差異がクライアントへ漏れている。** `AnimalImage.fromJson` が `type` で分岐し、
   Cataas は ID から URL を組み立て、Dog CEO は URL をそのまま使う、という知識が Dart 側にある。
   取得元を差し替えるたびにクライアントの改修とアプリ配布が必要になる。
2. **障害時の扱いが弱い。** `fetchImages` は例外を握りつぶして空リストを返すため、
   「取得できなかった」のか「そもそも 0 件だった」のかを UI が区別できない。
   タイムアウトも再試行も設定されていない。
3. **Web では CORS が外部 API の設定に依存する。** 取得元を増やすたびに相手側の CORS 設定に左右される。
4. **秘密情報の置き場がない。** API キーを要する取得元（#34 の The Cat API 等）を追加すると、
   Flutter Web の配布物にキーが載る。`--dart-define` はビルド成果物に埋め込まれるため秘密の保管場所にならない。
5. **「今日の1枚」(#35) のようなサーバー側でしか正しく決められない機能を実装できない。**
   クライアント側の日付計算では端末時計を信用することになる。

一方で、画像そのものを自前 DB／ストレージへ全面移行する案は、転載条件、削除要求への対応、
ストレージ・転送料、運用負荷が現時点の規模に対して過大である。

## 決定

**Firebase Functions を BFF として導入し、Firestore はメタデータと短期 TTL キャッシュに使うハイブリッド構成を採用する。**
画像本体は引き続き外部配信元を参照し、自前保存はしない。

```text
Flutter PWA
    ↓ HTTPS（Hosting rewrite /api/** → Functions）
Firebase Functions / API v1  (asia-northeast1)
    ├─ Cataas adapter
    ├─ Dog CEO adapter
    ├─ 将来追加する外部 API adapter
    └─ Firestore（TTL キャッシュ・今日の1枚）
```

### 内部構造（純粋コアと副作用の分離）

```text
functions/src/
  core/validate.ts        allowlist 入力検証
  core/imageUrl.ts        HTTPS + 許可ホスト完全一致の検証
  core/httpClient.ts      タイムアウト・再試行・バックオフ
  core/aggregate.ts       並行呼び出しと部分失敗の集約
  core/daily.ts           今日の1枚
  adapters/*.ts           外部 API ごとの取得と正規化
  cache/store.ts          CacheStore インターフェース・TTL 定数・キー生成
  cache/firestoreStore.ts CacheStore の Firestore 実装（唯一 firebase-admin に依存）
  http/handler.ts         ルーティングとステータス／ヘッダー決定
  index.ts                firebase-functions への配線
```

`firebase-admin` / `firebase-functions` へ依存するのは `cache/firestoreStore.ts` と `index.ts` だけである。
集約ロジックは `fetch` / `CacheStore` / `now` / `random` / `sleep` を注入して受け取るため、
**単体テストは実ネットワークにも Firestore エミュレータにも一切触れずに実行できる**。
これは「タイムアウト、部分失敗、全体失敗の挙動をテストできる」という完了条件を満たすための中核的な設計判断である。

### 主要な仕様

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| バージョニング | パスに `/api/v1` | 破壊的変更時に v2 を並走させる |
| `types` | allowlist `cat` / `dog`。未知の値は 400 | 任意の値を素通しすると SSRF・オープンプロキシの入口になる |
| `limit` | 1..30、既定 10 | 既存クライアントが 10 件単位で山札を補充している。上限は外向き通信量とレイテンシの抑制 |
| 1 試行タイムアウト | 3 秒 | スワイプ体験は待たせられない。3 秒を超える取得は失敗として次の補充へ回す方が体験がよい |
| 再試行 | 追加 1 回（合計 2 試行） | 冪等な GET のみ。一過性の失敗は 1 回で大半が回復し、それ以上は総レイテンシを悪化させるだけ |
| バックオフ | 初回 200ms、2 倍ずつ、上限 1000ms、フルジッター | 同時失敗時のリトライ集中（thundering herd）を避ける |
| 再試行対象 | ネットワークエラー／タイムアウト／5xx／429 のみ | 429 を除く 4xx は再試行しても結果が変わらない |
| Functions タイムアウト | 20 秒 | 最悪ケース（3s + 1s + 3s）を十分に上回りつつ、暴走時の課金を抑える |
| 一覧キャッシュの鮮度 (`expiresAt`) | 5 分 | 結果自体がランダムなので長い TTL は「新しい画像が来ない」体験になる。外部 API 負荷とのバランス点 |
| stale cache 許容 | 取得から 60 分以内 | 全滅時のみ使用。1 時間を超えた内容を「今の結果」として返すのは誤解を招く |
| 一覧の物理削除 (`purgeAt`) | 取得から 60 分 | Firestore の TTL ポリシー対象。鮮度と物理削除を分けないと、stale フォールバックを使いたい瞬間に document が削除対象になる |
| 今日の1枚 `expiresAt` | 次の JST 深夜 0 時まで | 日付は JST 固定。端末時計に依存させない |
| 今日の1枚 `purgeAt` | 次の JST 深夜 0 時 + 24 時間 | 日付が変わればキーも変わるが、削除直後の競合を避けて猶予を持たせる |
| CORS | `https://animal-swipe-596cc.web.app` のみ完全一致でエコー | `*` を返さない。ただし CORS は認証の代替ではない |

### 判定ルール（成功／部分成功／全体失敗）

| ケース | HTTP | ボディ |
| --- | --- | --- |
| 入力検証エラー | 400 | `INVALID_ANIMAL_TYPE` / `INVALID_LIMIT`。外部 API は呼ばない |
| 全プロバイダー成功 | 200 | `partial: false`, `warnings: []` |
| 一部プロバイダー失敗 | 200 | `partial: true` + `warnings[]`（取得できた `items` は返す） |
| 全滅 + 許容範囲の stale cache あり | 200 | stale な `items`、`partial: true` + `STALE_CACHE_SERVED` |
| 全滅 + stale cache なし | 502 | `UPSTREAM_UNAVAILABLE` |
| 未知のパス | 404 | `NOT_FOUND` |
| GET / OPTIONS 以外 | 405 | `METHOD_NOT_ALLOWED` |
| 想定外の例外 | 500 | `INTERNAL_ERROR`（内部詳細は返さない） |

上流障害に 500 を使わないのは、「BFF 自身のバグ」と「外部 API の障害」を
監視・アラート上で切り分けられるようにするためである。

### `id` の安定性と重複排除

- `id` は `"{source}:{providerStableId}"` 形式。
- Cataas: 外部が返す `id`（または `_id`）を使う。
- Dog CEO: ID を返さないため、検証済み画像 URL のパス（`breeds/pug/x.jpg`）を安定 ID とする。
  同一画像 URL は常に同一 `id` になる。
- 集約時に `id` で重複排除する。

### 「今日の1枚」の一意性

- 日付は JST で決める（`jstDateString`）。端末時計に依存しない。
- 選出結果の保存は **create-if-absent**（Firestore ではトランザクション）で行う。
  同時リクエストがそれぞれ別の候補を選んでも、確定するのは最初の 1 件だけで、
  競合に負けた側も確定済みの 1 件を返す。「今日の1枚」が閲覧者ごとに違う事態を防ぐ。
- 共有キャッシュの `s-maxage` は「返した `date` に対応する期限」から算出する。
  現在時刻から引き直すと、処理中に JST 深夜 0 時を跨いだ場合に前日の 1 枚を
  新しい日付いっぱい CDN へ載せてしまう。跨いだ場合は `no-store` にする。

## 非目的

- 初期段階から独自の動物画像カタログを構築すること。
- 外部 API の画像を無条件に複製・再配布すること。
- 任意 URL を中継する汎用画像プロキシを提供すること。
- 本 ADR の実装と同時にユーザー認証を完成させること。
- 本 ADR の実装と同時に Flutter 側の取得先を切り替えること（フェーズ 5、別作業）。

## 却下した代替案

### 案 A: クライアント直叩きを継続する

- **利点**: 追加コストゼロ、インフラ運用なし、レイテンシに中継ホップが増えない。
- **却下理由**:
  - 秘密情報を持つ取得元（#34）を追加できない。Flutter Web の配布物は誰でも読める。
  - CORS が相手側の設定次第で、取得元の選択肢が狭まる。
  - 「今日の1枚」(#35) を端末時計に依存せず実装できない。
  - タイムアウト・再試行・部分失敗の方針が全クライアント（Web/Android/iOS）に重複実装される。
  - 外部 API の契約変更のたびにアプリ再配布が必要で、#44 のヘルス監視も置き場所がない。

### 案 B: 全面的に自前カタログ化する（画像を Cloud Storage へ複製）

- **利点**: 外部 API の可用性・契約変更から完全に独立。レイテンシとキャッシュを完全に制御できる。
- **却下理由**:
  - Cataas / Dog CEO の画像は転載条件が個別に明確でなく、無条件の複製・再配布は法的リスクを負う。
  - 削除要求への対応フロー（誰がいつ消すか）を運用として持てていない。
  - ストレージ・転送料が発生し、収益のない個人プロジェクトの費用対効果に合わない。
  - 初期カタログの規模を確保するまで、スワイプ体験に必要な枚数を供給できない。
- 将来、利用条件を確認できた画像やユーザー投稿画像に限り再検討する（issue のフェーズ 7）。

### 案 C: Cloud Run + 独自コンテナ

- **利点**: ランタイム自由度が高く、コールドスタートを常駐で回避できる。
- **却下理由**: 既に Firebase Hosting を使っており、Hosting rewrite で同一オリジン配信できる
  Functions の方が構成要素が少ない。トラフィック規模的に常駐インスタンスの費用対効果がない。

### 案 D: Firebase Hosting のみで外部 API へリバースプロキシする

- **利点**: コードを書かずに CORS 問題だけは解決する。
- **却下理由**: 正規化も部分失敗の集約もできず、実質的に「任意 URL 中継」に近い形になる。
  非スコープとして明示的に排除している構成である。

## トレードオフ / 受け入れるコスト

| 受け入れるもの | 緩和策 |
| --- | --- |
| BFF が単一障害点になる | 全滅時の stale cache、部分失敗時の縮退返却、`maxInstances` によるコスト暴走の抑止 |
| 中継ホップによるレイテンシ増（コールドスタート含む） | 同一リージョン（asia-northeast1）、5 分 TTL キャッシュ、`concurrency: 40` でインスタンス再利用 |
| Functions 呼び出し・Firestore read/write の従量課金 | TTL キャッシュで外部呼び出しと read を削減、`maxInstances: 5`、予算アラート（手順は `functions/README.md`。**本 PR では未設定**） |
| Node/TypeScript という第二の言語が増える | 純粋コア中心の小さな構成に保ち、依存を最小化（実行時依存は firebase-admin / firebase-functions のみ） |
| 外部 API のレスポンス形状を実接続で検証できていない | tolerant parsing（`id` / `_id` の両対応、不正要素はスキップ）と #44 の契約テストで補う |
| Flutter 側が切り替わるまで新旧 2 経路が併存する | フェーズ 5 で切り替え。BFF の共通形式は既存 `AnimalImage` に写像可能な形にしてある |
